# Pantheon 2.0 — Modern Install, Settings UI, and Update Flow

Status: design (approved direction, implementation queued as 2.0.x/2.1 work).
References studied: opencode-quota, opencode-anon-turn, ECC, quire.sh,
opencode-update-notifier, opencode-synced, opencode-usage-monitor,
opencode-models-discovery, awesome-opencode, npm-12 script policy.

## 1. Install — the npx path dies for OpenCode 2.x

### The happy path (matches opencode-quota exactly)

```bash
opencode plugin add pantheon-opencode        # npm, or a git URL
# restart OpenCode, then:
/pantheon Add CSV export to the reports page
```

- One entry loads the server AND the TUI (our package already ships both).
- Global via `~/.config/opencode`; per-project via the project config.
- Manual setup stays documented for people who edit `opencode.json(c)`
  themselves (one `plugins` entry, `{ package, options }`).

### What happens to the installer

- `npx pantheon-opencode init` becomes the **1.x migration path only**
  (the `@4 init` pattern quota uses for its legacy line), plus an opt-in
  project-scaffolding tool (agents/skills/commands copies, worktree box).
- The 2.0 default flow never requires it. `pantheon-opencode doctor`,
  `reconcile`, and `update` survive as the maintenance CLI.
- The V1→V2 config heal (singular `plugin` key → plural `plugins`,
  `.ts` path → directory) keeps running from both paths.

## 2. `/pantheon-settings` — the settings window

One window, one section per page, keyboard-first (`tab` cycles sections,
`esc`/`q` closes — the whats-new and dispatch windows are the code
templates). Every section writes to an existing mechanism; the UI is
deterministic sugar, not a second brain. Shipped as of 2.0.0-beta.2:

| Section | Writes to | Shipped in |
|---|---|---|
| Gates & Overrides | global `pantheon-overrides.json` (disable; `replace` content preserved across toggles; corrupt file refuses writes; project entries read-only) | beta.1 / beta.2 guards |
| Decision Model | `<config>/pantheon/decision-router.json` `enabled` flag (schema v2 exact keys, 0600, applies live) | beta.2 |
| Model Preset | `<config>/opencode/.pantheon/active-preset.json` (version-1 marker, `.bak` backup; `none` deletes) | beta.2 |
| J1 Risk Gate | nothing — env-only config (`PANTHEON_J1_*`), status rows + restart hint | beta.2 (status) |
| Updates | `~/.local/state/pantheon/update-check.json` (Check now probes the registry dist-tag of the running channel) | beta.2 |
| Doctor | nothing — file-derived health: install-version drift (H2), Node floor, overrides (K), decision-config validation | beta.2 |
| About | nothing | beta.1 |

Deferred: **Budgets** (the ledger is SQLite — the fail-open window does not
edit it), a **J1 file surface** (needs the runtime plugin to read a file at
setup), and a persisted **update-channel preference** (needs the CLI
`update` to honor it).

Expansion contract: a new setting = one entry in a registry + one row in a
section, with the pure state in a TUI-local module (self-contained bundle
doctrine) and a drift-pinning test against the canonical source. Nothing
else moves. The window reads state through the same file shapes the plugin,
installer and doctor consume — never a parallel format.

Non-goals: no config-file writer for arbitrary `opencode.json` keys (the
host owns those); no server round-trips (everything is local file state); no
credential, egress-consent or component wiring in the window (fail-open
means the window never owns a step that can fail closed).

## 3. Updates — pin, notify, adopt deliberately

Doctrine (update-notifier + npm-12 reality + our own fail-closed culture):
**never silent auto-update.** npm 12 blocks install scripts by default, and
floating ranges are the supply-chain attack surface.

- **Pin by default**: the installer/`plugin add` flow registers
  `pantheon-opencode@<exact>` — every upgrade is a reviewable config diff.
- **Notify**: a lightweight registry check (npm dist-tag latest vs the pinned
  version, TTL-cached, offline-safe) surfaces ONE toast/sidebar line:
  "pantheon-opencode 2.0.1 available — changelog: …". This is the same
  surface as the existing whats-new window, which already announces
  per-version changes from CHANGELOG.md.
- **Adopt**: `pantheon-opencode update` (already shipped) performs the bump
  with backup + reconcile; `/pantheon-settings → About` links the changelog.
- **Announce**: releases keep the Keep-a-Changelog entry; the whats-new
  window renders it on first boot after upgrade. Beta channel unchanged
  (`update` prefers beta until stable is chosen).

## 4. Ecosystem alignment

| Concern | Reference | What we take |
|---|---|---|
| Install + settings window | opencode-quota | one-command native install; tabbed window; npx only for the legacy line |
| Install alternatives | opencode-anon-turn | git-URL and plugins-directory installs documented |
| Multi-harness packaging | ECC | guided vs native setup separation; verified-channels warning |
| Verification posture | quire.sh | verify-before-users-do — matches our evals/gates |
| Update flow | opencode-update-notifier | pin + aggregate toast + deliberate adoption |
| Config portability | opencode-synced | global-config-as-repo pattern (our managed regions already support it) |
| Sidebar settings | opencode-usage-monitor | configurable refresh controls inside a sidebar |
| Model discovery | opencode-models-discovery | provider/model filtering for the Models tab |
| Ecosystem index | awesome-opencode | stay listed; watch the tui.json external-plugin loading caveat |

## 5. Implementation order

1. **Publish + install path** — npm publish (dispatch), README/INSTALLATION
   switch to `opencode plugin add`, npx demoted to migrator (docs + CLI).
2. **Overrides wiring (Fase 3)** — the Overrides tab needs the runtime
   consumer; do this first among features.
3. **`/pantheon-settings`, initial scope** — Gates + Overrides + About
   tabs (all state exists today). Models + Budgets tabs follow with the
   preset and cap registries. ("initial" is the window's first iteration —
   the repo no longer uses v1/v2 labels for anything.)
4. **Update notifier** — pinned-version check + toast, TTL cache, offline
   no-op; changelog link opens the whats-new window.
5. **Kill the npx default** — remove it from README quick-starts; keep
   `@1.x init` documented as the legacy migration.
