    Atualização do Pantheon¶

    English

    Este guia cobre dois movimentos: 1.5.2 → 1.6.0, uma atualização dentro da linha, e 1.6.x → 2.x, que cruza a fronteira de suporte do Pantheon. As versões de host suportadas e a evidência estão em Compatibilidade; esta página descreve as ações.

    Atualizando de 1.5.2 para 1.6.0¶

    Instale globalmente primeiro — update recusa cópias local, workspace e npx:

    npm install -g pantheon-opencode@beta
pantheon-opencode update            # canal beta do npm + refresh de config
pantheon-opencode update --stable   # canal estável

    update compara a versão instalada com a dist-tag do npm, executa npm install -g pantheon-opencode@<channel> e roda de novo init --yes --headless para que merges de config, o venv Python e as entradas MCP correspondam ao pacote novo. Artefatos de cópia (agents, skills, AGENTS.md, commands, scripts MCP, payload code-mode) são atualizados pelo postinstall em todo npm install.

    Depois da atualização:

    pantheon-opencode doctor

    doctor avisa quando o pacote é mais novo que a última sincronização e detecta drift de versão do plugin quando o caminho registrado aponta para uma cópia antiga em node_modules/pantheon-opencode.

    Se a atualização for interrompida, rode init de novo. Cada passo de cópia é idempotente por comparação de bytes, e o conjunto de backup exato em .pantheon/backups/<timestamp>/ é revertido com pantheon-opencode restore. Detalhes em Instalação.

    O que muda na 1.6.0¶

    • A superfície de tools V2 é de três tools incondicionais — hashline_edit, pantheon_cost, pantheon_model — mais até duas dependentes do host: vision_describe quando o host expõe o catálogo de modelos, e pantheon_bounded_read quando o host expõe as APIs de permissão e sessão (apenas sessões raiz do Zeus). Não são seis tools.
    • As três tools de goal do V2 não são registradas. O loop de goal precisa de GoalStore, GoalLoopClient e BackgroundJobBoard, que o PluginContext V2 não expõe. A lacuna é reportada como goal-tools.
    • Toda tool V2 declara output. O OpenCode 2.0.x rejeita uma tool cuja declaração e resultado não concordam.
    • Sessões read-only do V2 são aplicadas. Uma sessão delegada de apollo/gaia recebe deny para edit, write, bash, task, hashline_edit e pantheon_model pelo hook execute.before do V2.
    • Goals manuais duráveis passam para o MCP de Persistence. goal_create, goal_get, goal_update e goal_done são exclusivos do Zeus e escopados por sessão. As tools de goal V1 continuam disponíveis, mas depreciadas.
    • Tetos de passos são removidos em instalações V2. steps é opcional no OpenCode 2; ausente significa nenhum teto nativo. Rode o instalador uma vez para limpar um valor antigo de um agente gerenciado.
    • A memória ganha cap de 64 KiB e TTL, e pantheon_cost reporta USD por agente, modelo e sessão a partir do catálogo models.dev.

    Escolhendo a geração¶

    npx pantheon-opencode init --opencode-version v1
npx pantheon-opencode init --opencode-version v2
npx pantheon-opencode init --opencode-version auto

    auto é o padrão. --version v1|v2 continua aceito depois de init como a grafia legada. A ordem de resolução e o comportamento de fallback estão documentados uma única vez em Compatibilidade. auto nunca instala as duas gerações do plugin Pantheon.

    Checklist de migração¶

    1. Pare o OpenCode antes de trocar a geração do plugin.
    2. Rode init uma vez com o seletor desejado (v1, v2 ou auto). Não copie uma entrada de plugin V1 para uma lista plugins V2, nem o contrário.
    3. Se quiser a TUI, inclua o componente plugins do instalador. V1 usa tui.json; V2 usa os entrypoints nativos index.ts + tui.ts. Instalar apenas o plugin de servidor V2 não instala a TUI.
    4. Inspecione o resultado: entradas Pantheon V1 ficam em plugin; a entrada V2 é o diretório <installed>/src/plugin-v2 em plugins.
    5. Reinicie o OpenCode depois de mudar a configuração.
    6. Rode doctor e confirme que não resta drift de versão do plugin.

    Se o host cair na geração errada¶

    Uma instalação na geração errada significa que o gate não conseguiu ler o host; não significa que ele adivinhou. Passe --opencode-version v2 explicitamente, ou defina OPENCODE_VERSION=v2. Para ver o que o gate lê, rode opencode --version.

    Diferenças de runtime após a atualização¶

    • Delegação: nenhuma geração registra uma tool de delegação específica do Pantheon. Use o motor nativo de sessões filhas do host — subagent no runtime raiz relatado, task() na documentação de host/API. As antigas pantheon_delegate, pantheon_delegation_read e pantheon_delegation_list foram removidas.
    • V1: traz hashline_edit, as tools de goal/cost/model, o ciclo de vida do BackgroundJobBoard e os hooks V1 de evento/tool/compaction.
    • V2: não registra o BackgroundJobBoard, hooks V1 de evento/tool nem um hook de compaction V1. Ele adiciona os hooks V2 documentados em OpenCode 2.x.
    • Recuperação: ao reiniciar, jobs antigos ou em execução do board V1 são marcados como erro; não são retomados automaticamente e o trabalho filho não reinicia sozinho. O V2 não adiciona retomada/reinício automático.
    • Relatórios: os relatórios Markdown em .pantheon/delegations/ são saída histórica do board V1, não um protocolo de tarefa V2.

    Não descreva esta atualização como uma migração de paridade V1→V2. É uma escolha entre um plugin de runtime legado e um adaptador mais estreito, nativo do host.

    Perspectiva: 1.6.x para 2.x¶

    A partir da 1.7, o Pantheon abandona o contrato V1 e mira apenas o OpenCode 2. Hosts OpenCode 1.X não são suportados na 2.x. O suporte a OpenCode 2 já existe na 1.6.x, então a mudança da 2.x é a remoção do caminho V1, não um novo requisito de host.

    Prepare-se para a 2.x:

    • movendo goals manuais duráveis para as tools goal_* do MCP de Persistence;
    • removendo qualquer dependência das tools de goal V1 ou do BackgroundJobBoard;
    • confirmando que a instalação está registrada em plugins com o diretório <installed>/src/plugin-v2;
    • rodando doctor e as checagens de sandbox V2 descritas no Processo de release.

    Notas históricas de atualização¶

    Estas notas estão superadas e são mantidas para quem vem de linhas antigas.

    • v1.0 removeu todo o suporte multiplataforma; o Pantheon roda apenas no OpenCode. A instalação passou a ser npx pantheon-opencode init.
    • v3.19.0 introduziu o Memory Persistence Protocol. As regras obrigatórias de recall/store por agente são históricas: a política atual busca apenas quando o histórico do projeto pode mudar o resultado, reutiliza resultados do coordenador nas delegações e grava no máximo um resultado reutilizável de nível superior quando existe uma tool de escrita permitida. Veja Memória.
    • OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true não é pré-requisito universal. É um gate experimental de alguns runtimes e é definido pelo launcher npm run start do Pantheon; use apenas quando o runtime documentar e exigir.

    Para detalhe versão a versão, veja o changelog.
